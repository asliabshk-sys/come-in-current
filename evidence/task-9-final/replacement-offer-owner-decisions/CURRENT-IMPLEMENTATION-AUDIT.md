# T9-12 current implementation audit — 23 November 2026

**T9-12 remains NOT IMPLEMENTED** for timed expiry and independent cancellation. Baseline local and remote work were clean and matched `26188a861de92733301212a1cd97e64440fc4cbd`. This audit concerns post-order offers. Dated coupon/campaign windows and pre-checkout cart substitution are separate.

| Area | Retained implementation and evidence |
| --- | --- |
| Create or refresh | `backend/server.py` routes `POST /orders/{order_id}/replacements` and `POST /restaurant/orders/{order_id}/replacements`. Scoped shop/Restaurant owner or Admin reports the unavailable line. Grocery builds same-shop in-stock options; Restaurant validates same-restaurant menu choices and availability. Existing case replay returns the case; a qualifying refresh marks the prior case superseded and links it to the new case. |
| Stored dates and history | The order embeds the case with original financial and item snapshots, offered options, reporter, `reported_at`, optional supersession link/timestamp, and decision history. No authoritative `expires_at`, expiration cause, or independent cancellation field/state exists. |
| Customer response | The two `.../replacements/{case_id}/decision` routes require an authenticated owning customer. Supported actions are accept, reject and keep unavailable. Customer rejection concerns replacement options. Eligible continuation without the unavailable line can change the existing order under established rules. |
| Acceptance and financial safeguards | Options are revalidated against current catalog, stock/menu availability and relevant totals. Eligible orders are updated transactionally. Financially sensitive cases stay in COME-IN Assist with recorded customer intent and separate Admin review. An accepted intent in Assist can remain unresolved, unlike an applied `accepted` replacement. |
| Order and cart state | Grocery replacement order gates are `pending_payment`, `pending`, `accepted`, `preparing`. Restaurant substitutes `placed` for `pending`. Fulfillment progression is guarded where an open case would conflict. Pre-checkout cart replacement is a separate same-shop/category and stock-validated path with no effect on case expiry. |
| Permissions and whole-order cancellation | Customer cancellation is order-owner scoped. Grocery supports eligible pending/unpaid states and transactional stock restoration; Restaurant uses placed/pending-payment and its existing paid/state guards. Seller/Admin order status and Assist actions are separate. The two case decision routes do not give shop, Admin or delivery partner authority to decide for the customer. No independent case cancellation route was located. |
| Notifications and audit | Opening and applicable confirmed replacements use in-app notifications keyed to order kind, order ID and case ID. Case history includes actor, action, option, timestamp and previous order total. Financial review audit exists separately. There is no expiry/cancel notice or lifecycle audit for an independent case closure. |
| Retry and consistency | MongoDB transactions tie changes to the order and applicable catalog writes. Duplicate reports and identical decisions replay persisted outcome. Customer/order ownership and embedded case lookup reject unrelated cases. Some exact replays return before the state gate. They report a stored decision and do not make the case newly actionable. |
